**The actual burst mechanism is a false-failure loop caused by a 250 ms timeout on a multi-second command:**

- `profiles_actions.py:1107-1112` calls `call_async` **without** `timeout_s`, so it takes the default `timeout_s: float = 0.25` at `app/ipc_bridge.py:104`.
- That 0.25 s covers connect **and** the response read: `ipc_bridge.py:118-120` → `_run_call` → `IpcClient.connect(timeout=…)` + `client.call(..., timeout=…)`; `cli/ipc_client.py:136-144` wraps `readline()` in `wait_for` and converts to `IpcError(-1, "conexão timeout")`. There is **no retry** anywhere in `IpcClient`.
- Meanwhile the daemon has already accepted and is executing the whole activation (`daemon/ipc_handlers.py:374-492`: `clear_manual_trigger_active` → `manager.activate` → triggers + LEDs + keyboard + emulation + speaker + `materialize_launch_env`).
- So the GUI aborts the read, `_on_profile_switch_failure` (`profiles_actions.py:1124-1128`) toasts **"Falha (daemon offline?)"**, the row is never bolded and the selection is never re-synced — the user sees "nothing happened" and clicks "Ativar" again. - Contrast, in the same codebase: `footer_actions.py:236-242` uses `timeout_s=1.5` for `profile.apply_draft`; `ipc_bridge.py:523` uses `timeout=1.0`. `profile.switch` — by far the heaviest handler — is the one left at 0.25.
